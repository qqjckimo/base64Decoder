# URL Scissors — 效能框架與量測結果

量測日期 2026-11-05 · Chrome for Testing 153 · Linux 容器，Xvfb + openbox（真實視窗管理與焦點）
重現方式見 [`bench/README.md`](bench/README.md)。

---

## 1. 框架

| | 開啟效能（最高優先） | Runtime 效能（次之，投入較少） |
|---|---|---|
| 統計量 | **P75** | **P75** |
| 量什麼 | **真實按下快捷鍵** → 參數列畫出來 | **真實按鍵 / 點擊**（事件時間戳）→ 下一次 paint 之後 |
| 預算表達方式 | P75(產品) − P75(地板) | P75(產品) − P75(地板)；點擊類用絕對值 |

**為什麼用「相對地板的差值」當預算**：絕對毫秒數隨機器不同差好幾倍，但「同一個 surface 上，什麼都不做的 popup」和產品之間的差，才是我們的程式碼能影響的部分。換到哪台機器都能比較，也能拿來擋回歸。

**為什麼要 A/A 對照**：同時載入兩個一模一樣的地板（floorA、floorB）。它們的差就是量測雜訊；比雜訊還小的預算沒有意義。

**為什麼一定要真實輸入**：`chrome.action.openPopup()` 從程式碼開啟的 popup **不會授予 `activeTab`**，而產品只用 `activeTab`，所以只有 xdotool 送出的真實 X 鍵盤事件才是使用者實際走的路徑。

**為什麼每一次都是冷開啟**：量到 popup 關閉後 extension process **約 10ms 內就被回收**（每次重開都是新 pid）。沒有 service worker 的外掛，真實使用中不存在「熱」的狀態。所有開啟樣本都在確認沒有任何 extension process 存活之後才按鍵。

## 2. 開啟效能結果（最終程式碼，N=30/變體，交錯量測）

| 設定 | P50 | **P75** | P90 |
|---|---|---|---|
| 產品，**未釘選**（安裝後的預設） | 327.3 | **334.4ms** | 340.4 |
| 地板，未釘選 | ~307 | ~310ms | ~315 |
| 產品，**已釘選到工具列** | 70.1 | **74.9ms** | 78.8 |
| 地板，已釘選 | 45.5 | 50.0ms | 53.7 |

| 差值（P75，bootstrap 95% CI） | |
|---|---|
| 產品 − 地板（未釘選） | **+23.3ms** [16.2, 29.5] |
| 產品 − 地板（已釘選） | **+24.9ms** [19.5, 29.0] |
| floorA − floorB（**A/A 雜訊**） | +2.6ms [−4.6, 5.2] |
| **已釘選 − 未釘選** | **−259.4ms** [−265.3, −251.8] |

### 時間花在哪（產品，P75）

| 段落 | 未釘選 | 已釘選 | 誰的 |
|---|---|---|---|
| 按鍵 → popup 文件開始 | ~268ms | **~5ms** | Chrome（未釘選時要先播「把圖示彈出到工具列」的動畫） |
| 文件開始 → script 啟動 | 36.5ms | 35.7ms | Chrome（冷 process 載入第一個 script，地板一樣） |
| `chrome.*` binding 初始化 | ~1.0ms | ~1.0ms | 我們 |
| **IPC**（tabs + windows + storage 並行） | **18.1ms** | **19.9ms** | **冷 process 的第一次 IPC 往返** |
| render | 1.0ms | 1.3ms | 我們 |

三個 IPC 是**同時**回來的（19.8 / 19.9 / 20.0ms）：沒有哪一個特別慢，是冷 process 的第一次往返本身被卡住。熱 process 裡同樣的呼叫只要 ~1.8ms。

### 預算與判定

| 預算 | 實測 | 判定 |
|---|---|---|
| 開啟 P75 − 地板 P75 ≤ **30ms**（冷 process、無 keepalive） | +23.3 / +24.9ms，CI 上界 29.5 / 29.0 | ✅ |
| 結構：首次 paint 前**恰好一批**並行 IPC | 一批（3 個並行） | ✅ |
| 結構：開啟路徑上我們的 JS ≤ **3ms** P75 | binding 1.0 + render 1.0–1.3 ≈ 2.3ms | ✅ |

那 ~20ms 的冷 IPC 閘門是剩下唯一的大項，**不用 keepalive 就無法消除**（見 §5）。

## 3. 影片驗證：使用者實際看到什麼

in-page 計時只知道「頁面何時 paint」，不知道「使用者何時看見」。`bench/video.js` 用 ffmpeg 以 100fps 錄 X 畫面，逐幀分析 popup 的高度與內容（已釘選，各 8 次）：

| | P75 可見 | 第一個可見幀的高度 | 最終高度 |
|---|---|---|---|
| 產品 | 115.1ms | 452px | 456px |
| 地板 | 90.5ms | 450px | 456px |

- **沒有「空殼 → 長大」的兩段式出現**。產品第一個可見幀就已經是最終內容的高度。Chrome 會等內容畫好才顯示 popup，所以 load 之後才 render（`renderedAfterLoad = 30/30`）不會造成可見的跳動
- 但也代表 IPC 的 ~20ms **直接在「看得見」的路徑上**：可見時間差 25ms，與 in-page 差值吻合 —— 兩個獨立方法互相印證
- 兩者都有約 150ms 的淡入 —— 那是 Chrome 自己的 bubble 動畫，地板也一樣

## 4. Runtime 結果（真實 X 輸入，~14 鍵/秒）

| 互動 | 產品 P75 | 地板 P75 | 差值 / 預算 | 判定 |
|---|---|---|---|---|
| 打字（7 個參數） | 2.6ms | 2.3ms | +0.3ms [0.1, 0.7]，預算 ≤ +4ms | ✅ |
| 打字（16 個參數） | 3.9ms | 2.2ms | +1.7ms [1.4, 1.9]，預算 ≤ +4ms | ✅ |
| 點「+ 參數」 | 12.5ms | — | ≤ 16.7ms（一個 60Hz frame） | ✅ |
| 點「✕」刪除 | 11.7–12.6ms | — | ≤ 16.7ms | ✅ |

參數越多，打字越貴，主因是每次按鍵都要重新排版那行很長的預覽網址。仍遠在一個 frame 內，依框架不再深挖。

## 5. 被數據否決 / 修正過的判斷

| 原本的想法 | 數據 | 結果 |
|---|---|---|
| spike 量到 doc→rows ≈ 31ms，以為就是開啟成本 | 那是 SW 活著的**熱** process；真實每次都冷，而且之前沒量到「按鍵 → 文件開始」 | 框架改為真實按鍵起算、強制冷開啟 |
| 冷 process 的 IPC 慢，是 binding 延遲初始化 | binding 三個合計 1.0ms；三個 IPC 同時在 ~20ms 回來 | 是第一次往返的閘門，不是 binding，拿掉任何一個呼叫都沒用 |
| `?u=` 預載網址省 IPC | 真實 popup 上省 0.3ms，代價是 `tabs` 權限的安裝警告 | 放棄，維持只用 `activeTab` |
| load 之後才 render 會讓 popup 跳動 | 影片：第一個可見幀已是最終高度 | 不需要任何延遲 load 的 hack |
| 程式碼可以再壓 | 我們的 JS 在開啟路徑上約 2.3ms | 沒有可以再榨的 |

## 6. 已實作的開啟效能措施

- 單一 classic script、零 framework、零依賴、零 web font、inline critical CSS
- 首次 render 前**只等一批**並行 IPC（網址、視窗尺寸、per-tab 狀態），一次 paint 完成，不會在 paint 後改變尺寸
- `:root { color-scheme: light dark }` 放在 CSS 最前面，深色模式不白閃
- `<template>` cloning → 一個 `DocumentFragment` → 一次 append；事件委派
- `field-sizing: content`、`contain: layout style`，輸入時不需 JS 量測
- **釘選提示**：首次 render **之後**才呼叫 `chrome.action.getUserSettings()`，未釘選時把底部提示換成釘選建議 —— 替換同一行文字，不改變版面，所以不會在 popup 出現後造成位移。這是目前能影響的最大開啟效能槓桿（−259ms P75），但只能由使用者動手

## 7. 待你決定：keepalive service worker

| | |
|---|---|
| 效果 | 已釘選時 P75 **74.9 → 33.9ms**（−41.3ms [−44, −33]）；未釘選時 −50.4ms |
| 原理 | 每 30 秒用 `chrome.alarms` 喚醒一次 SW，讓 extension process 一直活著，popup 開啟不必建立新 process |
| 記憶體 | 常駐 **~25MB PSS**（RSS 92MB，其中多數是共享頁） |
| 其他代價 | 每 30 秒一次背景喚醒；需要 `alarms` 權限（無安裝警告）；Web Store 審核對「只為保活而存在的 SW」沒有明文禁止，但屬於灰色地帶 |
| 現狀 | **沒有加進產品**。只存在於 bench 的實驗變體（`BENCH_VARIANTS=keepalive`） |

這是用使用者的記憶體換開啟速度，對一個偶爾才用的工具是不是值得，是產品判斷，不是技術判斷。

## 8. 限制與未量測

- 所有絕對值來自 Linux 容器（無 GPU）。**比例**是穩健的結論，絕對值不代表桌機
- 只量了 Linux / X11。macOS 與 Windows 的圖示彈出動畫時間可能不同
- Runtime 的 P90 尾端（16 參數時打字 P90 5.4ms vs 地板 5.4ms，7 參數時 15.6 vs 4.4）未深究，框架只要求 P75
